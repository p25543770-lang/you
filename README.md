# Пульт оператора робота

Веб-интерфейс управления роботом для машины на Ubuntu. Робот поднимает свою
точку доступа Wi-Fi, телефон или ноутбук к ней подключается, и пульт открывается
в браузере. Доступ — только после авторизации с ролью **оператор**.

## Текущий объём (версия 0.1.0)

Сделано:

- вход оператора: логин + пароль, сессия в подписанной cookie; в средах, где
  cookie не сохраняются (iframe-превью), работает резервная подписанная
  URL-сессия `st` с отзывом при выходе;
- защита: хеш пароля PBKDF2-HMAC-SHA256, CSRF-токен, блокировка после серии
  неудачных попыток, безопасные заголовки (CSP, X-Frame-Options, nosniff);
- **после входа — веб-интерфейс робота RUS SLAM**: основной экран на `/`
  (схема шасси с 4 модулями, АКБ, тяга, маршрут, журнал событий; только просмотр) и инженерный
  пульт на `/console` (карта SLAM, сервис двигателей, телеметрия, «СТОП ТЯГИ» — программный стоп с командой на шасси);
- экран робота и kiosk-пульт хранятся локально в `slam_gui/` (из
  [danilka-revin/rus_slam](https://github.com/danilka-revin/rus_slam)); в киоске
  функции, включая руление и тягу, доступны без PIN, а PIN требуется только для
  открытия грузового кейса;
- прошивки `firmware/motor_master` и `firmware/motor_node` (руль v2): четыре Arduino Mega
  по I²C (один master, slave-адреса 2/3/4), сделаны по скетчу, проверенному на железе
  (`firmware/reference/`): ноль руля по оптодатчику D18 — кнопка «Калибровка», 10 кГц,
  команды монитора `k c d h s g p z`; проверены симуляцией четырёх плат и сборкой avr-gcc;
- страница **«Аккумулятор»** бортового экрана — нажать на панель АКБ: вся информация
  JBD BMS (банки, защиты, счётчики срабатываний, температуры, паспорт, пороги) и
  подключение BMS прямо с экрана, без правки `.env`;
- приложение и киоск обновляются одной fast-forward-кнопкой **«Обновить с GitHub»**
  после входа (в шапке главного экрана и инженерного пульта, на служебных
  страницах — плавающая кнопка справа внизу): скачивание → переустановка
  зависимостей → сборка-проверка → перезапуск; dirty tree и diverged-ветка не
  перезаписываются;
- настройки лидара — кнопка **«Лидар»** в шапке пульта и **«Настройки»** на
  бортовом экране: порт, протокол, скорость, линия мотора и автопоиск пишутся
  в `.env` и применяются сразу; киоск подхватывает изменения сам, запись
  доступна без PIN. Веб-пульт сохраняет вход оператора и CSRF-защиту;
- источник по умолчанию — USB-мастер четырёх Arduino (3 I²C-slave); симуляция включается явно, без платы экран честно показывает отсутствие связи;
- лидар 360° отдаёт **пакет ROS 2** (RPLIDAR A1/A2/A3/S1/C1 — `rplidar_ros`,
  LD06/LD19/STL-27L — `ldlidar_stl_ros2`, LDS-01/LDS-02 TurtleBot3 —
  `hls_lfcd_lds_driver`, лидар через плату OpenCR — `turtlebot3_node`):
  супервизор `zapret_lidar` сам подбирает драйвер, следит за свежестью `/scan`
  и пишет состояние в `/zapret/lidar/status`, а шлюзы берут скан из топика;
  ROS 2, драйверы и `ros2_ws` **докачиваются и компилируются сами** при запуске
  ярлыком (вручную — `./scripts/ros2_setup.sh`, ход — `--status`),
  `./scripts/ros2_lidar.sh --status` — проверка, причина «нет скана» пишется на
  экране и в `GET /api/lidar`; чтение USB-порта самим приложением сохранено как
  запасной путь (`RC_LIDAR_SOURCE=serial`), подтверждённый лидар **запоминается
  между перезапусками** (`data/lidar-found.json`), разовая проверка —
  `scripts/lidar_check.py`, стенд без железа — `scripts/lidar_sim.py`;
  подробности — `docs/ROS2_LIDAR.md`;
- макет как в референсе: служебная страница `/panel` — слева узкая колонка,
  в ней только бренд сверху и карточка пользователя (аватар, имя, роль, кнопка
  выхода) внизу; до входа колонки нет — форма входа центрирована на весь экран;
- скрипт точки доступа Wi-Fi через NetworkManager (`scripts/setup_ap.sh`);
- веб-пульт (8080) и киоск (8090) запускаются одним ярлыком **«Запустить робот»**;
  автозапуск после загрузки — только по желанию через systemd и одну запись сеанса;
- тесты: 577 проверок пройдено, 3 пропущено без `arduino-cli`/`colcon` (`pytest`), в том числе симуляция всех четырёх прошивок
  (нужен `g++`) и сборка avr-gcc (если задан тулчейн, см. `firmware/README.md`).

## Быстрый старт

### Ubuntu: скачать с GitHub и запустить одной командой

Нужен Python **3.9+** (на Ubuntu 22.04 и новее стоит по умолчанию; установщик
сам проверит версию и поставит `python3-venv`, если его нет).

```bash
git clone https://github.com/p25543770-lang/you.git robot-control
cd robot-control
./scripts/install_ubuntu.sh
```

Скрипт сам создаст `.venv`, поставит зависимости, сгенерирует `.env`, создаст
учётку оператора и ровно один ярлык **«Запустить робот»**. По умолчанию он
запустит оба интерфейса: веб-пульт на `http://<IP-машины>:8080/` и экран робота
на порту 8090. Следующие запуски — двойной щелчок по одному ярлыку. Если
установщик добавил пользователя в группу `dialout`, выйдите из Ubuntu и войдите
снова перед управлением Arduino по USB.

**ROS 2 для лидара ставится сам** — и установщиком, и ярлыком «Запустить
робот»: официальный репозиторий, `ros-<дистрибутив>-ros-base`, драйверы
лидаров (из apt, а чего там нет — клонируется и компилируется), `rosdep` и
`colcon build` рабочего пространства `ros2_ws`. Первый раз — несколько минут и
один вопрос пароля sudo в окне терминала, дальше — секунды (повторно
компилируется только то, что изменилось). Где готовых пакетов ROS 2 нет
(Debian, Raspberry Pi OS, не-LTS Ubuntu), ROS 2 компилируется из исходников в
фоне, а лидар пока читается по USB. Не нужен ROS 2 — `--no-ros2` (запомнится в
`.env` как `RC_ROS_AUTO=0`). Подробности — `docs/ROS2_LIDAR.md`.

> **Интернет не нужен.** Все пакеты (Flask, gunicorn, pip) лежат колёсами в
> `vendor/`. Если сети нет, установка идёт офлайн через
> `--no-index --find-links vendor`. Робот сам раздаёт Wi-Fi, поэтому у машины
> обычно нет интернета — это нормально, запуск всё равно работает. Интернет
> нужен один раз — чтобы докачать ROS 2 и драйверы лидара; без сети робот
> запускается как обычно (лидар по USB), а установка повторится при следующем
> запуске ярлыком.

### Если не открывается с другого устройства

- Адрес — строго **`http://IP:8080`**, а не `https://`: TLS не настроен, по
  https сервер не ответит. Если браузер сам подставляет https (Edge/Chrome
  «всегда HTTPS»), отключите это в настройках или выберите «продолжить по
  HTTP» на странице ошибки.
- Фаервол: `start.sh` сам открывает порт в `ufw`, если тот активен. Вручную:
  `sudo ufw allow 8080/tcp` (посмотреть правила: `sudo ufw status`).
- Сервер должен слушать `0.0.0.0`: в выводе `ss -ltn | grep 8080` слева должно
  быть `0.0.0.0:8080`, а не `127.0.0.1:8080`.
- Устройства должны быть в одной сети: с другого устройства должен проходить
  `ping <IP робота>`.

Полезные флаги: `--no-run` — установить без запуска; `--autostart` — поставить
автозапуск службой (без него приложение запускается вручную);
`sudo ./scripts/setup_ap.sh` — раздать на роботе свою Wi-Fi-сеть и подключаться
к пульту через неё.

### Один ярлык — оба интерфейса

Установщик создаёт один значок **«Запустить робот»** на рабочем столе. Он
проверяет зависимости один раз, поднимает веб-пульт и экран киоска вместе и
не создаёт дубли при повторном щелчке. Закрытие окна или Ctrl+C останавливает
запущенные этим ярлыком процессы; из терминала то же самое —
`./scripts/start_robot.sh`. Остановить вручную: `./scripts/stop.sh`.

Других ярлыков для пульта и киоска не нужно. Для установки вручную:
`./scripts/make_shortcut.sh`.

Обновление запускается кнопкой **«Обновить с GitHub»** в шапке веб-пульта
(главный экран и инженерный пульт; на служебных страницах `/panel` и `/service`
та же кнопка плавает справа внизу). Оно требует доступа машины к Git remote;
на роботе без интернета настройте доступ к локальному зеркалу репозитория.

## Обновить сервер и интерфейсы одной кнопкой

После входа нажмите **«Обновить с GitHub»** в веб-пульте. Полный цикл такой же,
как при ручной переустановке:

1. проверка ветки `RC_UPDATE_REMOTE`/`RC_UPDATE_BRANCH` (по умолчанию текущий
   `origin` и текущая ветка) и скачивание коммитов с GitHub (`git fetch`);
2. установка кода одним fast-forward (`git merge --ff-only`) — без
   `reset --hard`, грязное дерево и разошедшиеся ветки не затираются;
3. переустановка зависимостей: `scripts/ensure_deps.sh` каждый раз (он сам
   пропускает установленное и умеет офлайн из `vendor/`);
4. сборка-проверка: `compileall` всех модулей и импорт приложений интерпретатором
   `.venv` — битая версия не заменит работающую, код откатится назад;
5. перезапуск: веб-пульт (gunicorn/процесс `run.py`) и отдельный бортовой экран
   (8090), браузер ждёт новую версию и перезагружает страницу.

Прошивки Arduino хранятся в этом же Git-репозитории, но кнопка их не компилирует
и не прошивает платы — загрузите их вручную по `firmware/README.md`.
Для GitHub-клона, где стабильная ветка — `main`, при необходимости задайте
`RC_UPDATE_BRANCH=main` в `.env`. У машины должен быть сетевой доступ к Git
remote либо настроено локальное Git-зеркало; публичная Wi-Fi точка робота сама
по себе интернет не предоставляет.

## Бортовой экран робота (киоск, порт 8090)

На дисплее робота телеметрия, вкладка **«Настройки»**, BMS и остальные функции
доступны без PIN. Свайп вправо открывает руление и тягу, влево — камеры и логи.
PIN (`RC_SLAM_PIN`, по умолчанию `7232`) запрашивается только при открытии
грузового кейса; закрыть его можно без PIN. Отдельный веб-пульт оператора
сохраняет собственный вход и авторизацию.

**Важно: руление и тяга киоска теперь доступны без PIN и могут физически
перемещать робот.** Перед первым поворотом нажмите **«Калибровать все колёса»**
(или «Калибровка» у одного колеса): колесо идёт вправо до 100°, затем влево до
200°, находит флажок оптодатчика D18 и встаёт в его середину — колёса не должны
упираться, рядом никого. «0° вручную» — запасной вариант без датчика: сначала
выставить колесо прямо руками. Ноль сбрасывается после перезапуска платы.
Поворот — до ±85° влево и вправо (проверка в ПО: сервер, гейт движения и прошивка). Тяга ограничена ±20%, разрешена только при свежей телеметрии,
заданном нуле всех четырёх колёс и их выравнивании в пределах 2,5°. Кнопку
движения нужно удерживать; отпускание посылает тормоз, а аппаратный watchdog
останавливает моторы при потере heartbeat максимум за 650 мс. Это не аварийный
выключатель: первые проверки — только с вывешенными колёсами и подключённой
физической аварийной кнопкой.

### Страница «Аккумулятор» (4) — вся информация BMS и все банки

Открывается **нажатием на панель АКБ** на главном экране (там же подсказка
«Подробно: 12 банок и защиты →»), зелёной кнопкой **«АКБ подробно»** в шапке
или «АКБ» на панелях руления и камер. На странице: заряд, ток со знаком и
словом «заряд/разряд», мощность, ≈ Вт·ч, время до разряда или до полного
заряда, циклы; карта всех банок плиткой и таблица точных значений (мин/макс с
номером банки, разброс, сумма, балансировка); ключи, активные защиты и
счётчики срабатываний; температуры; имя платы, дата выпуска, прошивка; пороги
защит из памяти BMS. **«Скачать CSV»** — снимок всего этого.

Если BMS ещё не подключена, страница сама раскрывает **«Подключение BMS»**:
список портов с пометкой, чем занят каждый (мастер руля, лидар, шасси),
«Проверить выбранный» (одно чтение, в BMS ничего не пишется), «Найти
автоматически», «Сохранить и подключить» — порт пишется в `.env`
(`RC_BMS_PORT`) и опрос стартует сразу, без PIN.

Чтение — как в `danilka-revin/ploter_a1`: UART **9600 8N1**, только запросы
чтения (`0x03`, `0x04`, имя `0x05`, счётчики `0xAA`, пороги `0x10`–`0x2F`),
без заводского режима и записи. Опрос выполняет только сервер 8090. Подробно:
**[docs/battery.md](docs/battery.md)**.

### Открывается сам

```bash
./scripts/kiosk.sh            # зависимости + сервер на 8090 + экран в браузере
./run_kiosk.py                # то же самое напрямую, без виртуального окружения
```

| Адрес | Что там |
| --- | --- |
| `http://127.0.0.1:8090/` | редирект на экран (удобно для киоск-браузера) |
| `http://127.0.0.1:8090/kiosk` | сам экран |
| `http://127.0.0.1:8090/healthz` | проверка живости (JSON) |
| `http://127.0.0.1:8090/api/kiosk_state` | публичная телеметрия и доступность управления (JSON) |
| `http://127.0.0.1:8090/api/battery` | публичная телеметрия JBD BMS и всех банок |
| `http://127.0.0.1:8090/api/battery/report.csv` | свежий отчёт CSV по всем банкам |
| `GET /api/battery/setup` · `POST /api/battery/probe`, `/scan`, `/port` | подключение BMS со страницы «Аккумулятор»: порты, проверка, автопоиск, сохранение в `.env` (без PIN) |
| `POST /api/kiosk_calibrate` | калибровка руля по оптодатчику: `{"module": "FL"}` или `"ALL"`, доступна без PIN (`X-Robot-Control: steering`) |
| `POST /api/stop` | пульт 8080: СТОП тяги (PWM 0 + тормоз). Требует вход оператора и `X-Robot-Control: drive`; пересылается на бортовой экран и возвращает реальный итог. Без PIN — только для нулевой тяги |
| `http://127.0.0.1:8090/api/kiosk_logs` | настоящий журнал событий экрана: то, что показывает панель «Логи» (JSON) |
| `POST /api/kiosk_steer` | поворот одного модуля без PIN (`X-Robot-Control: steering`); payload строго `module` + `angle`, без команд тяги |
| `POST /api/kiosk_zero` | назначить программный ноль одного физически выставленного прямо модуля; без движения и без PIN |

### Панель «Логи»: настоящие события, а не демо-поток

Свайп влево открывает камеры и **журнал событий робота**. Панель берёт его из
`GET /api/kiosk_logs` — кольцевого буфера в памяти процесса (по умолчанию 400
записей, `RC_KIOSK_LOG_LIMIT`). Туда попадает всё, что действительно произошло:

* записи журналирования `robot_control.*` — найден лидар и на каком порту, что
  с портами шасси, когда открылся или закрылся экран в браузере, чем кончился
  перебор портов и что не сошлось в настройках;
* события маршрутов — открытие кейса по PIN (сам код PIN в журнал не попадает),
  «руление FL → +12.5°», «программный ноль выставлен», «тяга +8%» и «тяга 0% —
  тормоз», отказы команд с причиной.

Выдуманных строк в журнале нет: если событий не было, панель пишет «событий
ещё не было». Повторяющиеся события сворачиваются в счётчик («×25» — тяга
удерживалась), а не забивают экран. Подпись под панелью показывает число
записей, число ошибок, сколько старых вытеснено из буфера и источник данных.

Демо-поток (для проверки экрана без робота) включается только явно — `?demo=1`
в адресе или `localStorage.kiosk_demo = '1'` — и каждая его строка подписана
«демо». На пульте оператора (8080) тот же журнал отдаётся по
`GET /api/kiosk_logs` после входа; системные логи служб по-прежнему смотрят
через `journalctl -u robot-kiosk -f`.

Команда делает всё сразу: подтягивает зависимости, поднимает сервер на 8090
(пульт оператора занимает 8080 — они не мешают друг другу), **дожидается
ответа сервера и открывает экран в браузере в киоск-режиме** — без рамок,
адресной строки и вкладок. Если браузер закрыли, экран открывается заново
(отключается флагами `--no-watch` и `RC_KIOSK_WATCHDOG=0`).

Если сервер на 8090 уже запущен (например, службой `robot-kiosk`), повторный
запуск второй сервер не поднимает — он только открывает экран на дисплее.

Сам экран при этом не дублируется, сколько бы раз команду ни запустили
(автозапуск рабочего стола + ярлык + вручную): показ держит межпроцессный
замок `var/kiosk-display-8090.lock` на всё время жизни окна, и повторный
запуск, видя, что экран уже открыт, просто завершается. Браузеру для этого
даётся отдельный профиль (`~/.cache/robot-kiosk-browser`, меняется через
`RC_KIOSK_PROFILE_DIR`): без него Chromium передавал бы адрес уже работающей
копии и сразу выходил, а сторожевой таймер принимал это за закрытие окна и
открывал экран снова и снова. Если же браузер выходит почти сразу по другой
причине, пауза между переоткрытиями растёт (2 → 4 → 8 … до 30 с), а не
плодит окна очередями.

Каталог профиля создаётся до запуска браузера. Firefox с `--profile` сам
его не создаёт и иначе показывает **«Your Firefox profile cannot be loaded.
It may be missing or inaccessible.»** На Ubuntu Firefox (и часто Chromium) —
это snap: он не видит скрытые каталоги (`~/.cache`) и чужой `/tmp`. Для
snap профиль кладётся в `~/snap/<имя>/common/robot-kiosk-browser` — туда
snap писать может. Свой `RC_KIOSK_PROFILE_DIR` используется, только если
этот путь snap-у доступен.

Флаги: `--no-open` — только сервер (для службы или если графики нет);
`--open` — открыть экран принудительно; `--port 8091` — другой порт;
`--source sim|serial|ros|auto` — источник показаний.

### Автозапуск при входе в Ubuntu (по желанию)

По умолчанию приложение запускается вручную одним ярлыком **«Запустить робот»**
или командой `./scripts/start_robot.sh`. Для запуска серверов после загрузки и
открытия обоих экранов после входа в графический сеанс:

```bash
./scripts/install_ubuntu.sh --autostart
```

Установщик включает systemd-службы `robot-control` (8080) и `robot-kiosk` (8090),
а также добавляет **одну** запись автозапуска `~/.config/autostart/robot-control.desktop`.
Службы поднимают серверы; запись рабочего стола лишь открывает веб-пульт и киоск,
не создавая второй экземпляр. Логи: `journalctl -u robot-control -f` и
`journalctl -u robot-kiosk -f`. Чтобы включить это позже, используйте
`./scripts/autostart.sh on`; отключить — `./scripts/autostart.sh off`.

Остановить всё — `./scripts/stop.sh`: гасит пульт оператора и бортовой экран
(по pid-файлам, всю группу процессов — вместе с окном браузера), остановленные
службы `robot-control`/`robot-kiosk`, если они были запущены, и оставшиеся окна
киоск-браузера. Автозапуск `stop.sh` не выключает — за это отвечает
`./scripts/autostart.sh off` (см. ниже). Только серверы, без служб: `./scripts/stop.sh --servers`.

### Автозапуск: посмотреть, выключить, вернуть

```bash
./scripts/autostart.sh status              # что поднимается само (по умолчанию)
./scripts/autostart.sh off                 # выключить всё: автозапуск + остановить запущенное
./scripts/autostart.sh off --keep-running  # только выключить автозапуск
./scripts/autostart.sh on                  # вернуть автозапуск
```

Если автозапуск ставили старой версией кода (или руками), до обновления
пригодится то же самое по шагам:

```bash
sudo systemctl disable --now robot-control robot-kiosk   # службы: не стартуют после загрузки
./scripts/stop.sh                                       # остановить запущенное вручную
rm -f ~/.config/autostart/robot-control.desktop ~/.config/autostart/robot-kiosk.desktop  # старый автозапуск
sudo nmcli connection modify robot-ap connection.autoconnect no   # если точка доступа поднималась сама
crontab -l | grep -E 'start(_robot|_desktop)?\.sh|kiosk\.sh|run(_kiosk)?\.py'  # если прописывали в cron — убрать crontab -e
```

`off` — это «выключить всё, прямо сейчас»: он запрещает автозапуск **и**
останавливает запущенное. А именно:

- выключает и останавливает службы `robot-control`/`robot-kiosk`
  (`systemctl disable --now`);
- удаляет единый ярлык из автозапуска сеанса (`~/.config/autostart/robot-control.desktop`, а также старый `robot-kiosk.desktop`);
- запрещает автоподъём точки доступа Wi-Fi `robot-ap`;
- останавливает запущенные вручную серверы и окно киоска (`./scripts/stop.sh`);
- предупреждает, если строки автозапуска прописаны в cron (их скрипт не
  трогает: `crontab -e`).

Если нужно выключить только автозапуск, а работающее оставить до перезагрузки:
`./scripts/autostart.sh off --keep-running`.

### Хочу, чтобы всё запускалось само (при загрузке Ubuntu)

```bash

```

Установщик ставит и запускает две службы — `robot-control` (8080) и
`robot-kiosk` (8090) — с перезапуском при падении, а также одну запись
автозапуска рабочего стола `robot-control.desktop`, которая открывает оба экрана.
Логи: `journalctl -u robot-control -f` и `journalctl -u robot-kiosk -f`.

Окно терминала не закрывается само: ярлык запускает `start_desktop.sh`,
который после остановки сервера ждёт нажатия Enter — видно и статус,
и текст ошибки, если что-то пошло не так.

### Лидар: почему нет скана и как это починить

Скан 360° приходит из **ROS 2**: драйвер производителя (`rplidar_ros`,
`ldlidar_stl_ros2`, `hls_lfcd_lds_driver`, `turtlebot3_node`) публикует
`sensor_msgs/LaserScan` в `/scan`, а пульт и бортовой экран подписываются на
топик через `rclpy`. Кто именно запускает драйвер, решает супервизор
`zapret_lidar` (пакет в `ros2_ws/`): он сам подбирает пакет под подключённый
лидар, следит за свежестью скана и публикует состояние в
`/zapret/lidar/status` — оно видно в `GET /api/lidar` → `ros.supervisor` и в
панели «Лидар».

ROS 2, пакеты драйверов и сборка `ros2_ws` делаются **сами** при запуске
ярлыком «Запустить робот» (он же поднимает супервизор лидара до пульта и
экрана). Вручную и для проверки:

```bash
./scripts/ros2_setup.sh            # всё само: ROS 2, драйверы (apt/исходники), rosdep, colcon build
./scripts/ros2_setup.sh --status   # идёт ли установка, чем закончилась, конец журнала
./scripts/ros2_lidar.sh            # запустить драйвер лидара (или --service для автозапуска)
./scripts/ros2_lidar.sh --status   # топик /scan, частота, состояние драйвера
.venv/bin/python scripts/lidar_check.py --ros   # дистрибутив, rclpy, пакеты драйверов
```

Полный разбор пути ROS 2 (модели, установка, служба, диагностика) —
`docs/ROS2_LIDAR.md`. Чтение USB-порта самим приложением осталось запасным
вариантом: `RC_LIDAR_SOURCE=serial` (или `auto` на стенде без ROS 2) — тогда
работает всё описанное ниже.

Порядок источников задаёт `RC_LIDAR_SOURCE`: `auto` (по умолчанию) — ROS 2, если
он есть в системе, иначе USB; `ros` — только ROS 2 (USB-порт приложение не
открывает вовсе: его держит драйвер); `serial` — только USB.

На экране под картой пишется причина, а не просто «скана лидара нет»:
`GET /api/lidar` отдаёт её в поле `reason` (там же `detected`, `candidates`,
`hint`), а для ROS 2 — блок `ros` (дистрибутив, топик, публикаторы, драйвер и
его состояние). Подпись берётся оттуда же, поэтому по одному взгляду на экран
видно, что делать.

Что делает сервер сам:

- помнит найденный лидар между перезапусками: подтверждённые порт, протокол,
  скорость и линия мотора пишутся в `data/lidar-found.json` (видно в
  `GET /api/lidar` → `remembered`), и новый поиск проверяет их **первыми** —
  после ребута скан появляется за секунды, а не после полного обхода портов.
  Подсказка не заменяет перебор: лидар переехал на другой USB — он будет найден
  как обычно (закреплённые вручную `RC_LIDAR_PORT`/`RC_LIDAR_PROTOCOL` всегда
  важнее подсказки);
- перебирает **все** USB-порты: сначала `RC_LIDAR_PORT` (если задан), затем
  `/dev/rplidar*`, `/dev/serial/by-id/*lidar*`, а после них — все
  `/dev/serial/by-id/*`, `/dev/ttyUSB*` и `/dev/ttyACM*`; каждый круг начинается
  со следующего порта, поэтому поиск не «залипает» на одном USB. Порт из `.env` —
  только первый в очереди, а не единственный. Порты мастера и модулей шасси из
  `RC_SLAM_PORT`/`RC_SLAM_PORTS` (и `RC_LIDAR_EXCLUDE`) не трогаются — про них
  пишется в подсказке статуса;
- показывает ход перебора: причина в статусе (`перебираю порты: 2 из 5 — ttyUSB1`)
  и список проверенных портов в `GET /api/lidar` → `tried`;
- подбирает протокол и скорость: RPLIDAR A1/A2M8 — 115200, A2M7/A2M12/A3/S1 —
  256000, C1 — 460800, LD06/LD19 и LDS-01/LDS-02 — 230400; у RPLIDAR опрашивает
  SCAN, у LD06/LD19 и LDS-01 просто читает поток (контрольная сумма пакета
  проверяется, у клонов с «нулевой» CRC проверка отключается автоматически);
- на 230400 живут сразу два лидара — LD06/LD19 (кадры `0x54 0x2C`) и
  LDS-01/LDS-02 от TurtleBot3 (кадры `0xFA`, 42 байта) — проверяются оба;
- не верит первому попавшемуся витку: у настоящего скана соседние точки идут
  шагом около градуса и закрывают весь круг, а «точки» из чужих байт (не та
  скорость, не тот протокол, постороннее устройство на порту) либо прыгают по
  всему кругу, либо встают в одно направление — такой «виток» не считается
  находкой и не попадает на экран;
- один USB-порт не читают двое: лидар и источник данных шасси берут один и тот
  же межпроцессный замок порта (`data/lidar-<порт>.lock`). Пока порт не доказал,
  что он — модуль шасси, его читает только один процесс робота, и лидар всегда
  получает порт свободным; на подтверждённом порту модулей замок снимается,
  чтобы пульт и бортовой экран читали телеметрию как раньше. Без этого пульт
  (8080) и бортовой экран (8090) читали один порт вдвоём (pyserial:
  `device reports readiness to read but returned no data (… multiple access on
  port?)`), а лидару не доставалось ни секунды — он сообщал «занят» на всех
  портах, хотя порты держало это же приложение;
- пока лидар ищет свой порт, источник данных шасси не занимает USB-порты своей
  проверкой: уступка видна в `GET /api/lidar` (`priority_s` — сколько секунд
  осталось) и длится окно `RC_LIDAR_PRIORITY_S` (20 с) от начала поиска.
  Окно ограничено: лидара на роботе может не быть вовсе, и бесконечная уступка
  оставила бы экраны без телеметрии модулей. `RC_LIDAR_PRIORITY_S=0` отключает
  уступку (модули проверяют порты всегда, лидар ищет между их кругами);
- порт, на котором **подтвердились** кадры телеметрии, помечается в
  `data/ports/chassis-ports-<pid>.json` — лидар его вообще не перебирает (в
  `tried` он виден как `модуль шасси`, в статусе — `chassis_ports`), а источник
  шасси продолжает читать модули и во время поиска лидара, поэтому телеметрия на
  экранах не пропадает. Отметка живёт, пока на порту идут кадры: порт замолчал
  (модули переставили, в порт воткнули лидар) — отметка снимается, и перебор
  лидара снова включает этот порт;
- одна попытка на порту ограничена по времени: если на порту чужое устройство
  с непрерывным потоком (телеметрия модуля, GPS), перебор идёт дальше, а не
  висит на этом порту;
- не залипает на порту, у которого встал передатчик: команда лидару (`SCAN` у
  RPLIDAR, `b` у LDS-01) пишется с таймаутом. Без него pyserial ждёт готовности
  порта бесконечно, и один залипший USB-адаптер навсегда останавливал поток
  поиска лидара — на экране застывала старая причина, а порт так и не находился;
- включает мотор RPLIDAR линией USB-переходника, перебирая варианты
  DTR/RTS и их уровни (`RC_LIDAR_MOTOR`, по умолчанию `auto`);
- не отдаёт на экран «скан» из случайных байт: виток публикуется только
  целиком (≥ 20 точек).

Если скана нет, пульт и бортовой экран автоматически показывают диагностику
USB/serial: обнаруженные порты, права чтения/записи пользователя службы и
исключения портов мастера/шасси. Она доступна также в `GET /api/lidar`
(поле `usb_diagnostics`). Проверка не открывает порты и не мешает работающим
устройствам. Доступный USB-порт сам по себе не означает, что лидар отвечает:
подтверждение подключения — только свежий скан (`connected: true`).

### Настройки лидара с экрана (не руками в .env)

Кнопка **«Лидар»** в веб-пульте и **«Настройки»** на бортовом экране открывает
панель: живой статус (`connected`, устройство, причина «нет скана», USB-диагностика,
строка ROS 2 — дистрибутив, топик, драйвер, Гц), источник данных
(`auto` — ROS 2, если он есть, иначе USB; `ros`; `serial`),
порт (пусто — автопоиск, список найденных портов подсказывается), протокол
(`auto|rplidar|ld06|lds01`), скорость, линия мотора RPLIDAR и автопоиск по всем USB.
**«Сохранить и применить»** проверяет значения, пишет их в `.env` (`RC_LIDAR_*`,
остальные строки не трогаются) и перезапускает поиск лидара сразу — перезапуск
приложений не нужен; **«Пересканировать»** запускает поиск заново с текущими
настройками, а при источнике `ros` — просит супервизор ROS 2 заново подобрать
драйвер (сервис `~/rescan`). На пульте запись закрыта входом оператора и CSRF; в киоске настройки
доступны без PIN. Активный serial-поиск киоска прерывает чтение старого порта,
если другой процесс изменил `.env`, и сразу начинает новый круг. API:
`GET/POST /api/lidar/settings`, `POST /api/lidar/rescan` у обоих приложений.

Почему раньше «на вебе лидар подключён, а на борту нет»: процесс бортового
экрана брал готовый скан у пульта по HTTP, но следующий круг перебора начинал
ротацией со следующего порта и уходил подбирать параметры чужих USB-устройств.
Подбор занимает секунды…минуты, а скан считается свежим 1 секунду — борт почти
всё время честно писал «скана нет». Теперь порт, с которого сосед отдаёт скан,
запоминается и каждый круг начинается с него, а если у борта своих портов-кандидатов
нет вовсе (или сосед отдаёт скан по ROS/HTTP), peer-скан всё равно проверяется.

Проверка вручную — две команды: первая про железо, вторая про экраны.

```bash
.venv/bin/python scripts/lidar_check.py            # что видно на портах и почему
.venv/bin/python scripts/lidar_check.py --save-env # + записать найденное в .env
.venv/bin/python scripts/lidar_web_check.py        # дошёл ли скан до пульта и борта
dmesg | tail                                       # видит ли лидар система
```

Проверить стенд **без настоящего лидара** (и вообще без железа) можно
симулятором: он сыплет в свой псевдотерминал настоящие кадры LDS-01/LD06/
RPLIDAR — приложение их видит точно так же, как кадры с USB:

```bash
.venv/bin/python scripts/lidar_sim.py --protocol lds01 --symlink /tmp/lidar_sim
# в другом терминале — те же проверки, что и с настоящим лидаром:
.venv/bin/python scripts/lidar_check.py --port /tmp/lidar_sim
RC_LIDAR_PORT=/tmp/lidar_sim ./scripts/start.sh    # или весь пульт целиком
```

Если с симулятором скан доходит до экранов, а с настоящим лидаром — нет, дело
в железе/порту (кабель, `dialout`, другой адрес в `/dev/serial/by-id/…`); если
не доходит и с симулятором — смотрите таблицу причин ниже. Симулятор не трогает
настоящие `/dev/ttyUSB*`.

`lidar_check.py --save-env` пишет в `.env` найденные `RC_LIDAR_PORT` (постоянное
имя `/dev/serial/by-id/…`, если оно есть), `RC_LIDAR_PROTOCOL`, `RC_LIDAR_BAUD`
и `RC_LIDAR_MOTOR`, не трогая остальные строки файла, и создаёт `RC_SECRET_KEY`,
если `.env` ещё не было (без него сессии слетают при каждом перезапуске).
`--env-file /путь/.env` — записать в другой файл.

`lidar_web_check.py` проверяет остаток пути — то, что обычно и ломается: оба
приложения запущены, запущены интерпретатором с `pyserial` (`.venv`), и их
`GET /api/lidar` отдаёт **свежий настоящий** скан, а не демо. Коды возврата:
`0` — реальный лидар виден на обоих экранах; `1` — приложения работают, но
реального скана нет (причина и подсказка печатаются); `2` — приложение не
запущено. Флаги: `--wait 20` (ждать свежий скан), `--only console|kiosk`,
`--json`.

| Причина в статусе | Что делать |
| --- | --- |
| `ROS 2 не установлен (нет /opt/ros/…)` | запустить робота ярлыком «Запустить робот» — ROS 2 докачается и скомпилируется сам (вручную: `./scripts/ros2_setup.sh`; или оставить USB-путь: `RC_LIDAR_SOURCE=serial`) |
| `… нужен пароль администратора …` | ярлык открывает терминал — ввести там пароль sudo один раз |
| `… сейчас идёт автоустановка ROS 2 …` | подождать; ход — `./scripts/ros2_setup.sh --status` |
| `ROS 2 есть, но /scan никто не публикует` | драйвер лидара не запущен: ярлык запускает его сам; вручную — `./scripts/ros2_lidar.sh`, автозапуск — `./scripts/ros2_setup.sh --service` |
| `нет ROS 2-пакетов драйверов лидара` | `./scripts/ros2_setup.sh` (поставит из apt или скомпилирует из исходников) |
| `ни один драйвер не отдал /scan (…)` | `./scripts/ros2_lidar.sh --status`, права на порт (`dialout`), правильный порт; подробнее — `docs/ROS2_LIDAR.md` |
| `нет библиотеки pyserial` | `.venv/bin/pip install pyserial` (или `./scripts/ensure_deps.sh`) — пакет уже лежит в `vendor/` |
| `порт лидара не найден` | система не видит ни одного USB-порта: проверить кабель, `ls /dev/ttyUSB*`, `dmesg \| tail` |
| `порт … не открылся` + `dialout` | `sudo usermod -aG dialout $USER`, затем перезайти в систему |
| `лидар не ответил ни на одном из N портов (…)` | перебор прошёл все порты и не нашёл лидар: другая скорость (переключатель 115200/256000 на USB-адаптере A3), питание/кабель или лидар висит на порту, который отдан шасси (см. подсказку про `RC_SLAM_PORTS`). Если в списке есть `занят` — порт держит кто-то другой; чаще всего это источник данных шасси, он отпускает порт через пару секунд, и перебор сам повторяет попытку (см. ниже) |
| лидар TurtleBot3 (LDS-01) не найден | он идёт на 230400 кадрами `0xFA`; проверьте `.venv/bin/python scripts/lidar_check.py --protocol lds01`. Если лидар подключён к плате OpenCR (как в заводской сборке Burger), напрямую по USB его не видно: скан должен отдавать ROS 2 (`/scan`), либо подключайте лидар USB-переходником |
| `скан берётся у второго процесса робота` | так и должно быть: порт держит пульт или борт, скан приходит по HTTP (`source: peer`). Проверить, что точки свежие — `.venv/bin/python scripts/lidar_web_check.py` |
| `порт … занят другой программой` | чаще всего это **свой** источник данных шасси (`RC_SLAM_SOURCE=auto/serial`): он берёт порт на короткую проверку и отпускает его через пару секунд, поэтому перебор сам повторит попытку — делать ничего не нужно. Если порт занят постоянно — его держит пульт (8080), киоск (8090), `rplidar_ros` или Serial Monitor; второй процесс робота берёт скан у первого по HTTP, а постороннюю программу надо закрыть |
| `device reports readiness to read but returned no data (… multiple access on port?)` в журнале пульта или киоска | один и тот же USB-порт читали два процесса робота: байты доставались тому, кто успел, а второй получал от pyserial эту ошибку. Так было до общего замка порта: пульт (8080) и бортовой экран (8090) поднимают источник данных шасси и лидар одновременно. Если строка всё ещё появляется — порт читает посторонняя программа (`rplidar_ros`, Serial Monitor), закройте её |
| `скан устарел (…)` | лидар отвечает, но перестал сыпать точки: питание, мотор, кабель |

Ход перебора видно и в статусе: `GET /api/lidar` отдаёт `tried` — список проверенных
портов с результатом по каждому (`данные пошли`, `нет данных`, `занят`).

Проверка без пульта (порт никто не должен держать): `.venv/bin/python
scripts/lidar_check.py --port /dev/ttyUSB0 --baud 256000`.

### Лидар TurtleBot3 Burger (LDS-01 / LDS-02)

Лидар Burger'а — LDS-01 (он же HLS-LFCD2): 230400 бод, кадры по 42 байта с
заголовком `0xFA`, 60 пакетов по 6 измерений на виток (360 точек, ~5 Гц).
Протокол подбирается автоматически, вручную он называется `lds01`
(`RC_LIDAR_PROTOCOL=lds01`, синонимы `lds-01`, `hls-lfcd2`, `turtlebot3`).

Что делает приложение с этим лидаром:

- посылает команду запуска `b` (нужна прошивкам до 2017.10, новым не мешает) и
  **не** посылает команду остановки `e`: мотор должен крутиться и после
  закрытия порта, иначе каждый перебор упирался бы в раскрутку;
- проверяет контрольную сумму пакета (у клонов с другой формулой она
  отключается автоматически, поток при этом подтверждается по строгому порядку
  номеров пакетов `0xA0…0xDB`);
- считает углы как драйвер ROBOTIS (`359° − номер точки`, против часовой от
  направления вперёд) — карта совпадает с ROS-режимом, где этот лидар работает
  штатно;
- выбрасывает точки с флагом «измерение недостоверно» (старший бит слова
  дальности) и обрезает служебные биты слова.

Разовая проверка:

```bash
.venv/bin/python scripts/lidar_check.py --protocol lds01        # найти сам
.venv/bin/python scripts/lidar_check.py --port /dev/ttyUSB0     # конкретный порт
```

### Один лидар на два экрана (пульт 8080 и борт 8090)

USB-порт один, а веб-приложения два. Порт держит тот процесс, который поднял
лидар первым; второй его **не отбирает** (иначе скан теряли бы оба), а берёт
готовый виток у первого по HTTP — адреса в `RC_LIDAR_PEER_URLS` (по умолчанию
`http://127.0.0.1:8090/api/lidar` и `…:8080/api/lidar`, собственный порт
приложения из списка исключается). На экране это подписано честно:
`скан от пульта` (борт) или `скан от второго процесса` (пульт), в
`GET /api/lidar` — `source: peer`.

Чтобы не дёргать занятый порт по кругу, второй процесс открывает его только на
короткое окно проверки (отвечает ли лидар) и сразу закрывает, а дальше живёт на
чужом скане. Порты мастера и модулей шасси (`RC_SLAM_PORT`/`RC_SLAM_PORTS`) не
открываются вовсе — они исключены из перебора, и это видно в `usb_diagnostics`.

Источник данных шасси берёт тот же межпроцессный замок порта, что и лидар
(файл `data/lidar-<порт>.lock`): пока порт не подтвердился кадрами телеметрии,
читать его может только один процесс робота, поэтому «мусорных» одновременных
чтений одного USB-порта больше нет, а лидар получает порт свободным. Если в
статусе лидара написано `занят`, а в журнале — `порт занят (лидар или второй
процесс)`, это штатное ожидание своей очереди: шасси отпускает порт через пару
секунд, перебор повторится сам. Как только на порту пошла телеметрия модулей,
замок снимается — оба приложения читают модули как раньше.

Чтобы уступать порт **адресно**, а не «навсегда», процессы ведут общий журнал в
`data/ports/`: `lidar-state-<pid>.json` — что процесс делает с портами
(`searching` — ищет, `found` с именем порта — уже читает, `peer` — живёт на чужом
скане; плюс `since` — начало полосы поиска, чтобы окно приоритета не продлевалось
каждый круг), `chassis-ports-<pid>.json` — на каких портах у него подтвердились
модули. Файл = запись на каждый менеджер лидара в процессе; живым считается
только свежее состояние процесса, который ещё существует. Ни лидар, ни модули не
ходят на порт, который читает кто-то другой.

Лидар поднимается сразу при старте приложения, а не при первом запросе к карте,
поэтому скан появляется в первые секунды. `.env` читается до создания менеджера
лидара, так что `RC_LIDAR_*` действуют с первого запуска. Отключить автоподъём —
`RC_LIDAR_AUTOSTART=0`.

Демо-скан (`RC_SLAM_SOURCE=sim` или стенд без железа) всегда подписан
`демо · N точек (не лидар)`, а под картой остаётся причина, почему реального
скана нет: выдать демо за работающий лидар приложение не может. Флаг приходит в
API отдельным полем (`lidarDemo`/`demo`), и `lidar_web_check.py` на демо
возвращает `1`.

### Откуда берутся показания

Режим `master` выбран по умолчанию: Linux открывает один USB/UART мастера, а
тот опрашивает три платы по I²C. Если платы не подключены, приложение показывает
отсутствие телеметрии — не подменяет её симуляцией. Для стенда симуляцию включают
явно: `RC_SLAM_SOURCE=sim`; `auto`, `serial` и `ros` остаются доступными.

Какой источник используется, видно в чипе «сервер · …» и `GET /api/health`.
Мастер (прошивка руля v2) принимает адресное руление `w <FL|FR|RL|RR> <градусы>`,
калибровку по оптодатчику `w <module> calib` или `k` (все колёса), ручной ноль
`w <module> zero`, тягу `t <-20..20>` и тормоз `b`; в мониторе порта работают
команды проверенного скетча `k c d h s g p z`. После перезапуска платы ноль
задают снова (кнопка «Калибровать все колёса»). Подробно — `firmware/README.md`.

**До испытания тяги:** вывесить все колёса, проверить направления/полярность
входов и силовую схему, держать доступной физическую аварийную кнопку. Только
после этого разрешать краткий тест на 1–5% PWM. Не проверять тягу, когда колёса
стоят на земле. Веб-предел ±20% и watchdog 650 мс — дополнительная защита, не
замена аварийному отключению.

Замыкать реальные механизмы можно через переменные окружения
`RUS_SLAM_LOCK_CMD` / `RUS_SLAM_LOCK_CMD_CLOSE` (команда открытия/закрытия
замка) — без них ячейка отрабатывает вхолостую.

## Точка доступа Wi-Fi (робот сам раздаёт сеть)

Робот не подключён к интернету — он **сам является точкой доступа**. Телефон или
ноутбук подключается к его Wi-Fi и открывает пульт в браузере.

```bash
sudo ./scripts/setup_ap.sh                        # поднять (без автоподъёма при загрузке)
sudo ./scripts/setup_ap.sh --autostart            # поднять + поднимать при загрузке
sudo ./scripts/setup_ap.sh --status               # сеть, пароль, адрес
sudo ./scripts/setup_ap.sh --down                 # выключить
sudo RC_AP_SSID=ROBOT RC_AP_PSK='мой-пароль-8+' -E ./scripts/setup_ap.sh   # свои имя/пароль
sudo ./scripts/setup_ap.sh --iface wlp3s0         # конкретный адаптер
```

Или одной командой вместе с установкой:

```bash
./scripts/install_ubuntu.sh --ap --systemd
```

Скрипт создаёт в NetworkManager соединение `robot-ap` в режиме AP с адресом
`10.42.0.1/24` и раздачей DHCP (`ipv4.method shared`), включает captive portal
(телефон сам открывает страницу входа) и сохраняет пароль Wi-Fi в
`data/wifi.txt` (права `600`, в git не попадает). Пароль короче 8 символов
отклоняется; если `RC_AP_PSK` не задан и сохранённого нет — генерируется
случайный.

### Как подключиться

1. На телефоне/ноутбуке откройте список Wi-Fi и подключитесь к сети
   **`ROBOT-CONSOLE`** (пароль — в `data/wifi.txt` на роботе).
2. В браузере откройте **`http://10.42.0.1:8080/`** — именно `http://`, не `https://`.
3. Войдите под учёткой оператора (на роботе — в `data/credentials.txt`).

Нужен Wi-Fi-адаптер с поддержкой режима AP; при наличии `iw` скрипт это
проверяет и останавливается, если поддержки нет. Если адаптер был подключён к
другой сети, скрипт предупредит: интернет по этому Wi-Fi пропадёт (по кабелю —
останется).

## Учётки операторов

Пароль в открытом виде нигде не хранится — в `data/operators.json` лежит только
хеш, права на файл `600`, и в git он не попадает.

```bash
.venv/bin/python scripts/create_operator.py --username admin      # создать/сменить пароль
.venv/bin/python scripts/create_operator.py --list                # список
.venv/bin/python scripts/create_operator.py --username admin --disable
.venv/bin/python scripts/create_operator.py --username admin --check   # проверить пароль, не меняя
```

Роль одна — `operator`. Других ролей хранилище не принимает. Имя учётки может
быть любым, в том числе `admin`; роль от имени не зависит.

**По умолчанию установщик создаёт учётку `admin` с паролем `1234`** — её же
использует автозапуск. Переопределить можно переменными окружения:

```bash
RC_OPERATOR=robot RC_OPERATOR_PASSWORD='свой-пароль' ./scripts/install_ubuntu.sh
RC_OPERATOR_PASSWORD=random ./scripts/create_default_operator.sh   # случайный пароль
```

Логин и пароль дублируются в `data/credentials.txt` (права `600`, в git не
попадает). Сменить пароль позже:

```bash
.venv/bin/python scripts/create_operator.py --username admin --min-length 4
```

Пароль `1234` короткий: для отладки годится, для точки доступа, которую видит
всё вокруг, — лучше длиннее.

### Если вход говорит «Неверный логин или пароль»

1. Проверьте пароль вне браузера (так исключаются опечатки в форме и
   блокировка попыток):
   `.venv/bin/python scripts/create_operator.py --username admin --check`.
   Если скрипт говорит «НЕ совпадает» — задайте пароль заново (п. 2).
   Если «вход должен работать», а браузер отвергает — ждите 5 минут
   (блокировка после 5 попыток, п. 3).
2. Проверьте логин: по умолчанию — `admin` (регистр букв не важен).
   Пароль — в файле `data/credentials.txt` **на машине робота** (создаётся
   вместе с автоматической учёткой).
3. `RC_OPERATOR_PASSWORD` в `.env` действует только при **первом** создании
   учётки. Правка `.env` существующий пароль не меняет — задайте его явно:
   `.venv/bin/python scripts/create_operator.py --username admin --min-length 4`.
4. После 5 неверных попыток вход блокируется на 5 минут (ошибка 429) — даже
   верный пароль в это время не подойдёт. Подождите или перезапустите сервер.
5. Причина каждой неудачной попытки пишется в журнал сервера
   (`journalctl -u robot-control -f` или вывод окна `start.sh`):
   неверный пароль, отключённая учётка или отсутствие учёткок.
6. Проверьте раскладку и Caps Lock: пароль чувствителен к регистру
   (в отличие от логина).

## Тесты

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Проверяются: хеширование и сверка паролей, хранилище операторов, блокировка
подбора, вход/выход, доступ к панели только с ролью `operator`, требование
CSRF-токена, игнорирование внешнего `next`, заголовки безопасности, 404,
а также CLI создания учёток — ограничение длины пароля по умолчанию и через
`--min-length`, сверка двух вводов, создание из pipe через `--password-stdin`,
отсутствие пароля в файле в открытом виде, журналирование неудачных входов,
проверка пароля без смены (`--check`), стартовый листинг учёток —
и макет: левая колонка с пользователем только внизу, появляется после входа,
а до входа страницы отображаются без колонки. Отдельно покрыта резервная
URL-сессия: доступ к панели и выход по токену `st` без cookie, отклонение
подделанного токена и отзыв токена при выходе. CSRF-токен stateless (подписан
секретом и не зависит от cookie), поэтому вход работает и во встроенном
предпросмотре.

Прошивки руля проверяет `tests/test_firmware.py`: пины, уровни и скорости
сверяются с проверенным скетчем `firmware/reference/`, общий блок мастера и
слейва — побайтно, а `tests/firmware_sim/` собирает обе прошивки `g++` вместе с
моделями TB6600, оптодатчика D18 и шины I²C и прогоняет 22 сценария (калибровка
из разных положений, датчик пропал/залип, отмена, команды монитора, тяга и
watchdog, потеря слейва). Строки `@TLM` этой симуляции разбирает настоящий
серверный код. Без `g++` эти тесты пропускаются.

Путь «ROS 2 → /scan → экран» покрыт `tests/test_ros2_lidar.py` (пути `rclpy`
из `.venv`, статус и подсказки ROS 2, источник `auto|ros|serial`, блок `ros` в
`GET /api/lidar`, сервис пересканирования) и `tests/test_ros2_package.py`
(таблица драйверов и план запуска, опознание кадров LDS-01/LD06/RPLIDAR на
настоящем pty, `--print-plan`, package.xml/launch/config, `ros2_setup.sh --check`
на фальшивом префиксе ROS 2, `ros2_lidar.sh --print`, служба `robot-lidar`).
Автоустановка — `tests/test_ros2_autosetup.py`: `ros2_setup.sh` прогоняется на
фальшивой системе (подменены `apt-get`, `sudo`, `dpkg`, `curl`, `git`,
`colcon`, `rosdep`, `vcs`) — чистая Ubuntu, Linux Mint, Debian со сборкой ROS 2
из исходников в фоне, драйвер не из apt, нет пароля sudo, повторный запуск без
пересборки; плюс перезапуск приложений с окружением ROS 2, `--keep-alive`
супервизора и сборка `ros2_ws` настоящим colcon (если он установлен).

Путь «порт лидара → API → экран» покрыт тремя файлами: `tests/test_lidar_web.py`
(порт не отбирают друг у друга пульт и борт, скан берётся у второго процесса по
HTTP, демо не выдаётся за лидар, настройки из `.env` действуют с первого
запуска, оба API отдают один и тот же свежий скан — на фальшивом USB-порту),
`tests/test_lidar_deploy.py` (юниты стартуют из `.venv` и с `dialout`,
`ensure_deps.sh` ставит и чинит pyserial, `lidar_check.py --save-env` пишет
настройки, `lidar_web_check.py` различает реальный скан, демо и незапущенное
приложение) и `tests/test_gui_lidar_render.py` (отрисовка карты в `main.js` и
`robot.js` — нужен `node`, без него тесты пропускаются).

Бортовой экран проверяется отдельно (`tests/test_kiosk.py`): страница и
телеметрия отдаются без входа, `/` уводит на экран, в JSON нет данных замка и
журнала, экран открывается сам в браузере (заглушка вместо браузера), а если
браузер закрыли — открывается заново.

Если браузер не хранит cookie (iframe с opaque-origin), приложение переключается
на резервную URL-сессию: подписанный токен `st` добавляется в ссылки и формы,
а при выходе токен отзывается. Cookie остаётся основным механизмом; `st` —
только запасной для сред без cookie. Если и cookie, и `st` недоступны,
показывается подсказка открыть пульт в новой вкладке.

## Настройки

Все параметры — переменные окружения или файл `.env` (см. `.env.example`):
`RC_SECRET_KEY`, `RC_OPERATORS_FILE`, `RC_BIND_HOST`, `RC_PORT`,
`RC_COOKIE_SECURE`, `RC_MAX_FAILED_ATTEMPTS`, `RC_LOCKOUT_SECONDS`,
`RC_SESSION_MINUTES`, `RC_PBKDF2_ITERATIONS`, `RC_OPERATOR`,
`RC_OPERATOR_PASSWORD`.

Интерфейс робота:

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `RC_SLAM_SOURCE` | `master` | `master` \| `auto` \| `sim` \| `serial` \| `ros` — USB-мастер и три I²C-слейва (руление + тяга) |
| `RC_SLAM_PORTS` | автопоиск | UART-порты модулей через запятую (`/dev/ttyUSB0,…`) |
| `RC_SLAM_PORT` | `/dev/ttyACM0` | один UART мастер-платы для режима `master` |
| `RC_SLAM_LOCK_FILE` | `data/lock.json` | файл PIN-состояния и журнала грузового кейса киоска и ячейки хранения веб-пульта |
| `RC_SLAM_PIN` | `7232` | PIN открытия кейса в киоске и авторизации ячейки хранения/руления на веб-пульте (измените до эксплуатации) |
| `RC_SLAM_MAX_ATTEMPTS` | `5` | попыток ввода PIN до блокировки |
| `RC_SLAM_LOCK_SEC` | `30` | на сколько секунд блокировать после серии ошибок |

Лидар (`GET /api/lidar` отдаёт `reason`, `hint`, `detected`, `candidates`, `ros`):

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `RC_LIDAR_SOURCE` | `auto` | откуда берётся скан: `auto` — ROS 2, если он есть, иначе USB-порт; `ros` — только ROS 2 (драйвер держит порт, приложение подписывается на топик); `serial` — только USB-порт читает само приложение |
| `RC_LIDAR_ROS_TOPIC` | `/scan` | топик `sensor_msgs/LaserScan`, который слушают оба экрана |
| `RC_LIDAR_ROS_STATUS_TOPIC` | `/zapret/lidar/status` | топик состояния супервизора ROS 2 (JSON) — оттуда панель «Лидар» берёт драйвер, порт и частоту |
| `RC_ROS_PREFIX` | `/opt/ros/<дистрибутив>` | где искать ROS 2, если он установлен не в `/opt/ros` |
| `RC_ROS_AUTO` | `1` | `0` — ярлык и `ros2_lidar.sh` не ставят и не компилируют ROS 2 сами |
| `RC_ROS_DRIVERS` | пусто | свой набор драйверов лидаров для `ros2_setup.sh` (по умолчанию `hls_lfcd_lds_driver rplidar_ros ldlidar_stl_ros2 turtlebot3_node`) |
| `RC_LIDAR_PORT` | автопоиск | порт лидара: один, список через запятую или glob (`/dev/ttyUSB1`, `/dev/serial/by-id/*lidar*`). В ROS 2-режиме это порт драйвера, в USB-режиме — **первый** порт в очереди, остальные USB всё равно перебираются |
| `RC_LIDAR_BAUD` | автоподбор | скорость порта: `115200` (A1/A2M8), `256000` (A2M7/A2M12/A3/S1), `460800` (C1), `230400` (LD06/LD19, LDS-01/LDS-02) |
| `RC_LIDAR_PROTOCOL` | `auto` | модель лидара (она же протокол для USB-режима): `auto` \| `rplidar` \| `ld06` \| `lds01` (лидар TurtleBot3 Burger; синонимы `lds-01`, `hls-lfcd2`, `turtlebot3`). В ROS 2-режиме `auto` подбирает драйвер сам, а явное значение запускает соответствующий пакет (`turtlebot3`/`opencr` — лидар через плату OpenCR) |
| `RC_LIDAR_MOTOR` | `auto` | включение мотора RPLIDAR линией USB-переходника: `auto` \| `none` \| `dtr-low` \| `dtr-high` \| `rts-low` \| `rts-high` |
| `RC_LIDAR_AUTOPROBE` | `1` | `1` — сразу перебирать все `/dev/ttyUSB*`, `/dev/ttyACM*`; `0` — сначала только заданный порт и именованные symlink'и, а если там данных нет, следующий круг всё равно идёт по всем USB-портам |
| `RC_LIDAR_AUTOSTART` | `1` | поднимать лидар сразу при старте приложения; `0` — самому порт не открывать (скан берётся у второго процесса робота) |
| `RC_LIDAR_PRIORITY_S` | `20` | сколько секунд модули шасси не занимают USB-порты, пока лидар ищет свой; `0` — не уступать |
| `RC_LIDAR_EXCLUDE` | пусто | порты, которые лидару трогать нельзя (кроме мастера и модулей шасси) |
| `RC_LIDAR_PEER_URLS` | `http://127.0.0.1:8090/api/lidar`, `…:8080/api/lidar` | откуда брать скан, если порт занят вторым процессом робота |

Бортовой экран (киоск):

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `RC_KIOSK_PORT` | `8090` | порт экрана (пульт оператора — `RC_PORT`, 8080) |
| `RC_KIOSK_OPEN` | `1`, если есть дисплей | открывать экран в браузере; `0` — только сервер |
| `RC_KIOSK_WATCHDOG` | `1` | снова открывать экран, если браузер закрыли |
| `RC_KIOSK_BROWSER` | автопоиск | браузер для киоск-режима (chromium/chrome/firefox) |
| `RC_KIOSK_PROFILE_DIR` | `~/.cache/robot-kiosk-browser` | отдельный профиль браузера киоска (не даёт окну дублироваться). Для snap Firefox/Chromium скрытый путь автоматически заменяется на `~/snap/<имя>/common/robot-kiosk-browser`, иначе профиль «не загружается» |
| `RC_KIOSK_LOG_LIMIT` | `400` | сколько записей настоящего журнала держать в памяти для панели «Логи» (20…5000) |

При работе по HTTPS включите `RC_COOKIE_SECURE=true`, чтобы cookie сессии
помечалась как `Secure`.
